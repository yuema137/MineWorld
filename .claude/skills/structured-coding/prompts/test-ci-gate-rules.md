## TEST / CI / GATE EXECUTION RULES  
Permanent working rules for SIDERIUS development

These rules apply to every implementation PR unless a frozen task-specific  
design explicitly overrides them.

The goal is NOT maximal test count.

The goal is:

    every important failure class  
        has one appropriate canonical verification owner

while avoiding:

    duplicated coverage  
    fake lifecycle tests  
    redundant full-suite execution  
    expensive validation that proves nothing new.

### 0. CORE PHILOSOPHY

Testing layers are COMPLEMENTARY.

They are NOT:

    Unit proves everything  
    + Gate 1 proves it again  
    + Gate 2 proves it again  
    + full CI proves it again.

Instead:

    STATIC TOOLS  
    +  
    UNIT  
    +  
    GATE 1  
    +  
    GATE 2

jointly provide verification.

Conceptually:

    total verification  
        =  
    static analysis  
    ∪ deterministic local semantics  
    ∪ real LLM behavior  
    ∪ real production lifecycle

A meaningful behavior does NOT need a Unit test merely because it is important.

Some important behavior is honestly testable only in Gate 1 or Gate 2.

That is intentional.

For every proposed test or Gate, ask:

    What UNIQUE failure class does this own?

and:

    Why is this not already adequately owned by another layer?

"Extra safety" is NOT sufficient justification for duplicate coverage.

### 1. STATIC TOOL OWNERSHIP

Do not write Unit tests for properties adequately owned by static tooling.

RUFF / formatting owns things such as:

    formatting  
    import hygiene  
    many syntax/style errors  
    trivial unused symbols  
    lint-enforceable source properties

PYRIGHT owns things such as:

    static type compatibility  
    invalid typed calls  
    impossible assignments  
    typed protocol misuse detectable statically

PYDANTIC / SCHEMA LIBRARIES own ordinary field-level schema mechanics where  
the library itself already guarantees the behavior.

Do not create tests whose only claim is:

    "Pydantic rejects an obviously invalid Literal value"

unless the repository has an independent semantic requirement beyond ordinary  
Pydantic behavior.

Unit tests should remain for NONTRIVIAL semantic relations such as:

    cross-field constraints  
    fail-closed resolution  
    semantic compatibility  
    domain-specific invariants.

### 2. UNIT TEST OWNERSHIP

UNIT owns cheap, deterministic, local semantics.

Examples include:

    numerical/scientific oracles  
    deterministic arithmetic  
    contract resolution  
    protocol mapping  
    serialization/deserialization  
    identity / hashes / fingerprints  
    deterministic transforms  
    manifest derivation  
    scope/disjointness algorithms  
    deterministic state transitions  
    failure classification  
    pure policy logic  
    fail-closed behavior  
    registry resolution  
    codec behavior  
    local parser behavior  
    genericity structural guards  
    deterministic replay against frozen real evidence  
    narrow regression tests with strong localization.

A good Unit test answers:

    Given this explicit local state/input,  
    does this deterministic authority produce the correct local result?

Examples:

GOOD UNIT:

    given runtime components A/B/C,  
    deadline provider computes D

GOOD UNIT:

    given a frozen real sidecar payload,  
    provider parses it correctly

GOOD UNIT:

    given three hand-computed tensors,  
    FocalLoss returns the expected values

GOOD UNIT:

    missing registered capability fails closed

BAD UNIT:

    fake training lifecycle writes a fake sidecar,  
    fake watchdog observes it,  
    therefore real lifecycle must work

BAD UNIT:

    StubLLM returns hand-written JSON,  
    agent reaches completion,  
    therefore the real LLM behavior is validated

BAD UNIT:

    expected value generated by the same implementation under test

Unit must NOT become a fake Gate.

### 3. GATE 1 OWNERSHIP

GATE 1 owns behavior that fundamentally depends on a REAL LLM.

Typical Gate-1-owned claims:

    real prompt -> real model response

    real proposer generates usable structured output

    real implementor produces a valid candidate

    real LLM respects task contracts

    real LLM output survives schema/protocol boundaries

    real agent behavior reaches the intended next node

    real task-profile differences cause materially appropriate model behavior

Gate 1 should NOT be run merely because the project has a Gate 1.

Run Gate 1 only when:

    an LLM-facing semantic boundary changed

or:

    a task acceptance criterion specifically requires real LLM evidence.

Examples of changes that MAY require Gate 1:

    prompts  
    proposer behavior  
    implementor behavior  
    planner behavior  
    LLM-visible task facts  
    tool descriptions exposed to the model  
    structured generation contracts  
    model-facing error feedback.

Examples that normally do NOT require Gate 1:

    pure dataset reader change  
    deterministic metric implementation  
    local registry refactor  
    serialization fix  
    GPU measurement arithmetic  
    non-LLM runtime plumbing.

If no LLM-facing semantics changed:

    Gate 1 = NOT REQUIRED

Record that explicitly.

### 4. GATE 2 OWNERSHIP

GATE 2 owns REAL production lifecycle behavior.

Typical Gate-2-owned properties:

    real data loading

    real subprocess lifecycle

    real filesystem/process interaction

    real GPU execution

    real training

    real validation

    real inference

    real scoring

    real persistence timing

    real sidecar arrival/visibility timing

    real watchdog vs actual elapsed time

    real process cleanup

    real resource accounting

    complete production workflow reachability.

The decisive question is often:

    Could a Unit fixture manufacture the exact state whose ARRIVAL or TIMING is  
    the property under test?

If YES, the lifecycle property is probably Gate-2-owned.

Reference pattern:

UNIT owns:

    given verified timing components,  
    deadline arithmetic is correct

GATE 2 owns:

    the real validation process publishes the component early enough for the  
    watchdog to observe it.

Do not construct increasingly elaborate fake Gate-2 tests.

### 5. JUSTIFIED OVERLAP

Overlap between Unit and a Gate is allowed only when the layers own DIFFERENT  
properties.

Example:

Gate 2:

    real runtime produces a valid sidecar at the correct lifecycle moment

Unit:

    given a frozen production-shaped sidecar,  
    parser rejects malformed fields and computes local arithmetic correctly.

Another example:

Gate 1:

    real LLM generates schema-valid proposal

Unit:

    renderer contains the required contract  
    and deterministic parser rejects an invalid proposal.

Another justified overlap:

Gate 2 discovers a real defect.

Add a narrow Unit regression ONLY if the Unit test provides:

    precise local defect localization

and does NOT merely simulate the same real lifecycle again.

### 6. BEFORE RUNNING ANY VALIDATION

Before an expensive validation step, state the claim.

Use this mental template:

    CLAIM:  
        what exact failure class are we testing?

    OWNER:  
        static / Unit / Gate 1 / Gate 2 / CI

    EVIDENCE:  
        what observation distinguishes PASS from FAIL?

    COUNTERFACTUAL:  
        where useful, what mutation/broken implementation would make this RED?

    COST:  
        what is the cheapest authoritative test?

Do not run validation first and decide afterward what it supposedly proved.

### 7. DEVELOPMENT-TIME VALIDATION

During implementation, use TARGETED validation.

After one coherent semantic change:

    run only the tests/checks owned by the changed authority

then:

    update the design/execution ledger  
    commit the coherent change  
    continue.

Examples:

change numerical loss:  
    focused numerical Unit tests

change registry:  
    registry + consumers + fail-closed tests

change prompt:  
    prompt/schema Unit  
    + Gate 1 if real LLM behavior is affected

change training lifecycle:  
    local deterministic seam tests  
    + bounded Gate 2

change docs:  
    docs/guardrail checks only

Do NOT run the repository full suite after every commit.

### 8. LOCAL FULL-SUITE POLICY

LOCAL FULL SUITE IS NOT RUN BY DEFAULT.

This includes disguised variants such as:

    run directory A  
    then directory B  
    then directory C

until the whole repository has effectively been tested.

Chunking the full suite is still running the full suite.

Do not do it merely because the command is split.

Default:

    local full suite = 0 runs

Use local full suite only when there is a SPECIFIC reason that cannot be served  
by targeted tests or the formal PR CI.

### 9. THE ONE-EXPENSIVE-FULL-SUITE RULE

For one intended final executable head:

    expensive full-suite runs should normally be <= 1.

Normal workflow:

    local full suite:  
        DO NOT RUN

    manual remote workflow_dispatch full CI:  
        DO NOT RUN

    formal PR automatic CI:  
        RUN ONCE  
        this is the canonical full-suite evidence

Do NOT produce:

    local full suite  
    +  
    manual remote full CI  
    +  
    formal PR automatic full CI

for the same failure class.

More green runs do not make identical evidence more informative.

### 10. MANUAL REMOTE CI IS EXCEPTIONAL

Before manually dispatching an expensive full CI, ask:

    Will opening/retargeting the formal PR soon trigger substantially the same  
    CI on the same code?

If YES:

    DO NOT manually dispatch.

Manual full CI is appropriate only when:

1. automatic PR CI cannot be triggered;

2. the evidence is genuinely needed before a formal PR can exist;

3. another equivalent full-suite execution will not immediately follow;

or:

4. diagnosing the CI machinery itself specifically requires manual dispatch.

Document why the exception was necessary.

### 11. SELECTIVE PR CI

PR CI should preferentially run affected deterministic test areas rather than  
the entire repository when the selector can determine impact safely.

Model:

    changed source  
        ->  
    ownership/dependency selector  
        ->  
    relevant deterministic suites  
        +  
    Gate requirement classification.

The selector MUST FAIL CLOSED.

If impact is unknown:

    FULL SUITE

not:

    ZERO TESTS.

Broad/full fallback should normally apply to:

    selector implementation itself  
    CI workflow files  
    ownership/dependency manifests  
    tests/conftest.py  
    broadly shared test helpers  
    central registries  
    broad shared protocols/schemas  
    repo-wide guardrail infrastructure  
    unmapped production paths  
    selector errors.

Correctness first.

Do not optimize fallback rate before the selector is trustworthy.

### 12. FULL SUITE ROLE

The full Unit suite remains valuable.

Its role is a cross-module regression net.

Preferred architecture:

NARROW PR:  
    selective affected deterministic tests

UNKNOWN / HIGH-FANOUT PR:  
    full Unit suite

MASTER / NIGHTLY / SCHEDULED:  
    full Unit suite

MILESTONE / SEMANTIC VALIDATION:  
    Gate 1 / Gate 2 as required by ownership.

The full suite should not become the default blocking tax for every small PR.

### 13. STACKED PRs

For stacked development:

    PR A  
      -> PR B  
          -> PR C

REVIEW granularity and VALIDATION granularity are different.

You may review:

    A separately  
    B separately  
    C separately

while validating:

    targeted evidence per child  
    +  
    ONE full CI on the final integrated stack head.

Do not automatically run full CI on every child if the final stack will  
immediately run the same suite again.

Per child:

    targeted Unit tests  
    relevant Gate evidence  
    semantic ledger  
    coherent commits.

Final integrated head:

    one canonical full CI.

### 14. GATE WALL-TIME BUDGET

Gate 1 / Gate 2 may be run autonomously when authorized by the task.

Keep each individual Gate run bounded.

Default target:

    <= approximately 10 minutes per Gate run

unless a frozen design explicitly authorizes more.

If the natural experiment is too long, reduce:

    dataset subset  
    epochs  
    training steps  
    validation samples  
    inference samples  
    number of files

while preserving the REAL semantic path.

Do NOT satisfy the time limit by replacing:

    real LLM  
    real data  
    real GPU  
    real training  
    real validation  
    real inference  
    real subprocess

with a fake.

A bounded Gate must remain discriminative.

### 15. BEFORE A GATE RUN

Write the Gate specification BEFORE launching.

Record in the design ledger:

    Gate claim

    canonical owner

    exact executable HEAD

    exact command/config

    bounded subset/budget

    expected PASS evidence

    expected FAIL/counterfactual if useful

    why the bounded configuration still exercises the intended failure class

    evidence destination.

Do not invent the interpretation after the run.

### 16. AFTER A GATE RUN

Classify the run as exactly one of:

    PASS  
    FAIL  
    INCONCLUSIVE

EXIT CODE 0 IS NOT AUTOMATICALLY PASS.

Read the actual artifacts/logs.

PASS means:

    the semantic claim was exercised  
    and the required evidence was observed.

FAIL means:

    the intended semantic path ran  
    and contradicted the acceptance criterion.

INCONCLUSIVE means:

    the intended semantic claim was not actually tested.

Examples:

    API/provider outage  
    parser invocation mistake  
    unrelated infrastructure crash  
    missing environment resource  
    execution stopped before the relevant phase.

Record:

    exact HEAD  
    command/config  
    wall time  
    lifecycle stages reached  
    evidence/artifact location  
    decisive observation  
    PASS/FAIL/INCONCLUSIVE  
    next decision.

### 17. GATE FAIL POLICY

If Gate FAILS:

DO NOT immediately patch the test.

Audit source.

Determine whether the failure is:

    implementation defect

    incorrect child design assumption

    frozen parent/design invariant falsified

    unrelated infrastructure problem.

If implementation defect:

    fix owner  
    record finding/decision  
    targeted validation  
    commit  
    rerun bounded Gate.

If child assumption was wrong but parent contract still holds:

    amend child ledger/design honestly  
    implement the corrected path  
    continue.

If a frozen parent/public contract is falsified:

    STOP for operator review.

### 18. GATE INCONCLUSIVE POLICY

Do not blindly rerun an inconclusive Gate.

First diagnose why it was inconclusive.

Examples:

    wrong CLI flags  
    API timeout  
    provider failure  
    environment problem  
    unrelated process crash.

If the cause has a bounded, source-grounded fix:

    fix/retry autonomously.

Record failed invocation attempts.

Do not repeatedly spend Gate budget hoping the next run works.

### 19. GATE 1 / GATE 2 ARE NOT CI REPLACEMENTS

CI and Gates prove different things.

Example:

CI / Unit:

    registry resolves correct implementation  
    manifest arithmetic is deterministic  
    metric formula is numerically correct.

Gate 2:

    real data  
    -> real training  
    -> real validation  
    -> real inference  
    -> real scoring

Therefore a good feature PR may legitimately have:

    targeted Unit  
    +  
    bounded Gate 2  
    +  
    one final PR CI.

That is NOT redundant.

What is redundant is:

    local full Unit  
    +  
    manual remote full Unit  
    +  
    automatic PR full Unit.

### 20. EXACT-HEAD EVIDENCE

Validation evidence belongs to an EXACT commit SHA.

If executable/test/config behavior changes after a validation run:

    that evidence does NOT automatically validate the new HEAD.

Before final canonical CI:

    finish intended code  
    finish intended tests  
    finish intended design/ledger docs  
    commit all intended changes

THEN:

    final intended HEAD  
        ->  
    canonical PR CI.

Do NOT:

    CI green  
        ->  
    change code/tests/config  
        ->  
    claim the earlier CI proves the new head.

Docs-only changes that influence architecture, validation instructions,  
manifests, CI, or acceptance state should also be committed before final CI.

### 21. REVIEW AND CI SHOULD RUN IN PARALLEL

Do not unnecessarily serialize:

    wait for CI  
    then start review.

Preferred:

    open formal PR  
        ->  
    automatic CI starts

AT THE SAME TIME:

    operator reviews semantic diff / ledger.

If:

    review requires no change  
    +  
    CI green

then merge.

If review changes the head:

    let automatic CI rerun on the new merge candidate.

Use CI time productively.

### 22. COMMIT DISCIPLINE

After one coherent semantic change is complete:

    implement  
    targeted validate  
    update ledger  
    commit.

A commit should contain:

    one understandable semantic change  
    +  
    its tests/evidence  
    +  
    corresponding ledger update.

Do not keep a huge working tree waiting for one giant final commit.

Do not commit every trivial line independently.

Commit granularity follows semantic ownership.

### 23. DESIGN / EXECUTION LEDGER

For meaningful findings, record in real time:

FINDING  
    what happened

SOURCE AUDIT  
    exact files/symbols/evidence inspected

WHY IT MATTERS  
    which contract/failure class is affected

DECISION  
    what was chosen and why

IMPLEMENTATION  
    what changed

VALIDATION  
    targeted Unit / Gate 1 / Gate 2 / static / CI

DEVIATION  
    original expectation vs actual evidence

Do not reconstruct the story only after success.

Failed assumptions are evidence.

Keep them.

### 24. MUTATION / COUNTERFACTUAL EVIDENCE

Use mutation/counterfactual proof when it meaningfully establishes that a test  
is load-bearing.

Especially valuable for:

    numerical oracles  
    guardrails  
    parity tests  
    fail-closed behavior  
    previous escaped defect classes.

But do not require mutation proof mechanically for every test.

If mutation is impractical or misleading:

    say so honestly.

Do not claim a mutation proof that was not actually obtained.

### 25. SELF-REFERENTIAL TESTS ARE INVALID

Never let expected values come from the implementation under test.

Bad:

    expected = production_function(...)  
    assert production_function(...) == expected

Bad parity:

    "old implementation"  
        is actually a compatibility alias  
        of the relocated new implementation.

For frozen parity:

    capture expected evidence BEFORE the change  
    record source SHA  
    freeze immutable manifest/hash  
    compare new implementation against that frozen evidence.

Tests should not manufacture the answer they claim to verify.

### 26. PR TEST-OWNERSHIP DECLARATION

Every substantive feature PR/design should declare:

UNIT OWNERSHIP  
    exact deterministic failure classes

GATE 1 OWNERSHIP  
    exact real-LLM failure classes

GATE 2 OWNERSHIP  
    exact real-lifecycle failure classes

STATIC OWNERSHIP  
    Ruff/Pyright/schema properties not duplicated in Unit

CI IMPACT  
    affected semantic areas / selected suites  
    whether full-suite fallback applies.

This should be defined BEFORE implementation where practical.

### 27. NO TEST-COUNT KPI

Do not optimize for:

    maximum test count

or:

    arbitrary coverage percentage

or:

    "every function must have a test."

For a large system, exhaustive Unit testing is neither realistic nor desirable.

Optimize for:

    independent failure-class ownership  
    localization quality  
    real evidence  
    maintenance cost  
    execution cost.

A smaller honest test architecture is preferable to thousands of tests  
simulating production behavior poorly.

### 28. OUT-OF-SCOPE FAILURES

If validation discovers an unrelated existing defect:

    audit enough to determine that it is unrelated

then:

    create/document an issue if material  
    do not expand the current PR indefinitely  
    continue if current acceptance is unaffected.

Do not "fix the whole repository" while validating one feature.

### 29. DEFAULT AUTONOMY

The agent is expected to autonomously:

    choose targeted tests  
    run authorized Gate 1/Gate 2  
    diagnose failures  
    inspect source  
    use official/upstream documentation where repository evidence is  
    insufficient  
    fix ordinary defects  
    update ledger  
    commit coherent changes  
    continue.

Do not stop for routine test failures.

Stop only when:

    a frozen semantic contract must change  
    a parent design invariant is falsified  
    materially different scientific semantics require operator choice  
    safety/data integrity is at risk  
    or the PR is READY FOR OPERATOR REVIEW.

### 30. DEFAULT VALIDATION FLOW

The normal workflow for a feature PR is:

DESIGN  
    declare test ownership

IMPLEMENTATION COMMIT 1  
    targeted Unit/static checks  
    optional relevant Gate  
    ledger  
    commit

IMPLEMENTATION COMMIT 2  
    targeted Unit/static checks  
    optional relevant Gate  
    ledger  
    commit

...

FINAL IMPLEMENTATION HEAD  
    finish docs/ledger  
    commit

FORMAL PR  
    automatic canonical CI ONCE

IN PARALLEL  
    operator review

IF needed:  
    bounded Gate evidence already collected  
    or final Gate if specifically required

IF review changes code:  
    targeted recheck  
    commit  
    automatic PR CI reruns

FINAL:  
    exact merge-candidate HEAD  
    required Gate evidence PASS  
    canonical CI PASS  
    operator approval

    -> merge

### 31. QUICK DECISION TABLE

If the question is:

"Should I run a Unit test?"

Ask:  
    Is this deterministic/local and does it own an independent failure class?

If YES:  
    Unit.

If the question is:

"Should I run Gate 1?"

Ask:  
    Does the claim depend on a REAL LLM behaving correctly?

If YES:  
    Gate 1.

If the question is:

"Should I run Gate 2?"

Ask:  
    Does the claim depend on REAL data/runtime/GPU/subprocess/training/  
    validation/inference/scoring/timing?

If YES:  
    Gate 2.

If the question is:

"Should I run the full suite locally?"

Default:  
    NO.

If the question is:

"Should I manually dispatch full CI?"

Ask:  
    Will formal PR CI run substantially the same suite shortly?

If YES:  
    NO.

If the question is:

"Should every stacked PR get full CI?"

Default:  
    NO.

Use:  
    targeted child evidence  
    +  
    one integrated final-head CI.

If the question is:

"Gate exited 0. Is it PASS?"

Answer:  
    NOT UNTIL semantic evidence is inspected.

If the question is:

"My Unit test can fake the lifecycle state."

Ask:  
    Is arrival/timing of that state actually the property?

If YES:  
    Gate 2 owns it.

### 32. ONE-SENTENCE PERMANENT RULE

For every failure class, use the cheapest verification layer that tests the  
REAL property honestly; do not duplicate it at more expensive or less faithful  
layers, and do not run the same expensive full-suite evidence more than once  
without a concrete independent reason.
