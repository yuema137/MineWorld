## 2. Observable engine outcome and scope boundary

A synthetic authored world chooses either existing unitless hunger or one typed food-energy reserve model inside optional needs. The server consumes existing ItemsConsumed facts, uses configured daily use, preserves fractional energy, discloses truthful kcal/servings/bar data, and renders it identically in headless/agent/2D/3D paths. A second currency/configuration and creation-time removal require no business-rule edits. A synthetic market script purchases, consumes, saves, restarts and verifies the exact authoritative result without models. Invalid authored genesis produces an actionable terminal diagnostic before the CLI allocates SQLite or listens.

Food energy: integer numerator, D=C configured daily kcal, 86400 world seconds/day, no midnight reset or offline wall depletion, capacity cap and zero floor, no accumulated excess debt. In the example D=2000, initial reserve1500, at6h1000, +500→1500, at12h1000. Normalized hunger is an owner-derived deficit (at or above threshold motivates eating); the energy bar is the opposite reserve direction. Existing unitless behavior and tiredness remain. Initial1500 is a synthetic/example authoring choice, not a medical inference or conversion of hunger300.

Material infrastructure scope: generic InvalidGenesisContent construction error; lazy persistence backend factory and the two CLI new-save callers; SDK owner-version constants and authored cross-field validation/refusal hooks. No domain rules enter kernel/persistence/host. Reuse existing storage, integer arithmetic, dispatch, action and observation machinery; no dependency, data-owner facade, generalized resource framework or custom database.

Excluded: editing Market Town prices/people/shops/production; any claim of retail realism, autonomous 300-day food affordability or finished demo integration; old-save migration; currency redesign; hydration/illness/collapse; live system removal/rate mutation; sleep skip, home assignment, store hours, conversation/memory repair, launcher lifecycle repairs, platform deployment, public export/publication or paid inference. Content remains a distinct blocked checkpoint requiring ten sourced portion/price rows and reachable-policy/prefix-cash/stock proof. Existing S35 content acceptance is not reduced.

### Wire and display details added after consumer audit

The v2 needs record has `hunger_model: unitless|food-energy`. Unitless emits no food_energy. Food-energy emits `food_energy: {unit:kcal, available_kcal, capacity_kcal, use_kcal_per_world_day, bar:{value,maximum}, replaces_need:<need identifier>}`; needs sets `replaces_need` to its hunger key. This extra **owner-disclosed identity** lets a generic reader replace the corresponding deficit row without hardcoding hunger vocabulary. It is not a configurable renderer command, and the client never derives it from world name. The owner-provided bar uses value/maximum=0..1000/1000; display text shows numerator kcal/capacity and daily use separately. Typed serving descriptors accompany nourishment/kinds entries. Unitless and food-energy are exhaustive v2 variants, and malformed/incomplete food-energy must not become unitless fallback.

Existing `clients/protocol/mineworld/observation.gd::component_value` returns payload and loses the schema envelope. Needs readers will inspect their observer's component envelope directly (or a narrowly useful envelope accessor if justified in review), check schema, then decode. No need to change transport frame format. Preserve genuine schema1 unitless recorded observations as their own legacy read branch; do not accept missing/unknown schema as v2. Existing hand-built tests lacking schema must state schema1 explicitly; preserved recorded historical fixture bytes are not rewritten just to pass.

Keep `scripts/check_client_rules.py` R7 intact. `needs.gd` must name no hunger/tiredness/feeling literals and perform no `<`/`>` comparisons. Validate finite whole unsigned values through equality/type checks and range equality (e.g. integer equals its bounded clamp) inside its pure decode path; no thresholds, unit conversion or arithmetic that changes the owner's bar values. Replacing a row uses equality between its dynamic need identifier and `replaces_need`. Generic visual layout/rounding remains presentation only. If safe strict decoding cannot be implemented while preserving this guard, stop with the exact constraint and a reviewed bounded guard revision; do not bypass the checker or silently accept malformed values.

Agent needs models gain typed FoodEnergy/Serving records rather than adding an untyped dict. Its own record selector must retain schema before payload decode. LM Situation gains an optional typed energy summary and known nourishment/serving facts needed by its display; prompt adds one bounded owner-facts line, no new recommendations/planning policy. Existing word-based feeling trigger remains word-based; changes in numeric reserve alone must not cause inference every frame. The no-needs prompt golden remains unchanged. This PR does not claim a real model can plan a diet; real-LLM Gate is not required for that unclaimed behavior.
