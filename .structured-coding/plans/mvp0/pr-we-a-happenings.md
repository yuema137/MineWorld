## 1. Goal, in one paragraph

A MineWorld town today changes only through its people and its weather. WE-a adds the third source the
operator asked for: **happenings** — a Saturday market on the street, a festival in the park announced a week
ahead, a street musician on one day in seven — generated by a System Pack from the world's calendar and a
seeded integer draw, with no language model anywhere. `happenings` owns only its happenings. It announces,
begins and ends each one as a fact; every other System that wants to respond does so **in its own reduction,
from those facts, under its own opt-in configuration** — WE-a's worked example is `economy` lowering the corner
store's prices while a market day runs. A world author writes new kinds of happening in content
(`configure/happenings.yaml`) and a pack author writes new generators in code (an `ARC-62` catalog,
`HappeningGenerator`); both go through one admission path that also becomes, in WE-b, the path an LLM
director's proposals take. A world that does not enable the pack is byte-identical; a world that removes it
loads and runs.

## 2. Scope and non-goals

### 2.1 In scope

1. A new System Pack, `systems/happenings` (crate `mineworld-happenings`, system id `happenings`), installed
   by `ARC-33`'s two lines.
2. Its configuration, `configure/happenings.yaml`, decoded by its own types (`ARC-61`, plain
   `PackConfiguration`, §5.1): a content seed, a **kind catalog**, calendar entries, random entries, limits,
   and the list of external generators the world selects.
3. A daily, calendar-aware, integer, counter-seeded generation pass, driven by calendar's `day-began`, with two
   bundled generators (`calendar`, `random`) and one host that admits or withholds every draft (§5.3 … §5.5).
4. One `happening` Process per announced happening: announced → running → ended, with facts
   `happening-announced`, `happening-began`, `happening-ended`, and `happening-withheld` for refused drafts
   (§5.4).
5. An `ARC-62` extension catalog, `HappeningGenerator`, with its register function and an empty line in the
   installed set, so a separate System Pack can contribute a generator without editing `happenings` (§5.5).
6. Disclosure of the happenings at and announced for the observer's place (§5.7).
7. The first reacting System: `economy` gains an optional `configure/economy.yaml` with `price_modifiers`, and
   states its own `prices-adjusted` / `prices-restored` facts when a configured happening begins and ends
   (§6). Opt-in; absent by default.
8. Market Town opts in by configuration only (§7; operator ruling QWE-1 (a)), with a `scripts/baselines.txt`
   reason line.
9. Tests and mutation evidence (§9), the pack's README, the `systems/README.md` line, and a dated note to
   `ARC-88` (§12).

### 2.3 Invariants (frozen at freeze)

- **INV-WE-1 Byte identity when absent.** A world whose `systems:` does not list `happenings` produces the same
  facts, journal and snapshots as on the base, byte for byte. Checked for `social-cafe`, `lakeside`,
  `bodies-yard`, and for `market-town` before C5, by `scripts/ci_parity.py record` on base and head and
  `ci_parity.py diff` (§9.3).
- **INV-WE-2 Determinism.** The happening history of a world is a pure function of the World Pack (including
  `configure/happenings.yaml` and its `seed`), the code, and the calendar's days. No RNG state is kept; every
  draw is counter-based over `(seed, day index, stable key, index)`.
- **INV-WE-3 Single ownership.** `happenings` writes only its own Processes. It states no other pack's facts and
  writes no other pack's component. `economy` writes `Shop` only in reductions of its own facts.
- **INV-WE-4 Removability.** Removing `happenings` and its `configure:` entry leaves a world that loads and
  runs. A reacting pack whose configuration names happenings requires `happenings` (`ARC-61` `requires`), so
  removing one without the other is refused by name, never silently inert.
- **INV-WE-5 Unconfigured is silent.** Enabled without `configure/happenings.yaml`: no Process, no fact, no
  disclosure (AC-WE-3).
- **INV-WE-6 Hard limits.** `limits` are the host's, enforced on every draft from every generator; no
  generator can exceed them (AC-WE-4).
- **INV-WE-7 Integers only.** No floating-point type in the crate (weather's `tests/no_float.rs` precedent).
- **INV-WE-8 Kernel ignorance.** No kernel, contract, persistence or worldpack change. A happening kind is a
  slug `happenings` carries and never interprets (as `group-activity`'s `ActivityKind`).

### 3.2 Findings

- **F-WE-a-1 — there is no "world seed".** Step-24 §9.2 says random draws are keyed by "(world seed, day, kind
  index)". A world has no seed: `mineworld run --seed` seeds controllers (`ARC-27`), and replay never reads it.
  Weather's seed is content in its configure file. **Decision (bounded, recorded):** `happenings` takes
  `seed: u64` in `configure/happenings.yaml`, as weather does (QWE-6). Same seed → same history then holds
  across `run`, the hosted server and replay alike.
- **F-WE-a-2 — "IL section" does not fit.** Step-24 labels `configure/happenings.yaml` an "IL section", but its
  content (kinds, calendar, random, limits, seed) is not the six-key section shape, and `ARC-63` forbids a
  second file beside a section. **Decision proposed:** a plain `ARC-61` `PackConfiguration`, as calendar and
  weather (QWE-2). Consequence: audience narrowing comes from each kind's own `audience` field, bounded by the
  owner, not from `consequences:`.
- **F-WE-a-3 — no `worldpack` edit is needed.** DOC-24's `ARC-88` draft says "`worldpack` gains one key and one
  system id". Calendar and weather were added with no `worldpack` change; the loader learns packs only through
  `Capability`. WE-a changes no file under `worldpack/`. Proposed correction in §12.
- **F-WE-a-4 — kinds are content; generators are the catalog.** The `ARC-88` draft calls the *kinds* an
  `ARC-62` catalog. An `ARC-62` catalog is a trait with behaviour; a kind has none (it is a name, places, hours,
  an announcement horizon). Making kinds a code catalog would force a rebuild to add "a book fair". **Decision
  proposed (QWE-3):** kinds are content in the configure file; **generators** (code that decides *when*) are
  the `ARC-62` catalog. Both requirements of the operator ("their own kinds and generators") are met, each
  with the right tool.
- **F-WE-a-5 — 12d overlaps Market Town.** PR #171 re-baselines Market Town and edits economy's test support.
  C4 rebases over it; C5 (Market Town opt-in) starts only after it merges.
- **F-WE-a-6 — state in Processes, not a per-place component.** Step-24 says `happenings` "owns `Happenings` on
  the world's places". The calendar precedent keeps state in Processes and discloses declared records no entity
  carries; that writes nothing per place, keeps snapshots of non-participating places unchanged, and gives each
  happening one owner record. Adopted (bounded; the observable contract — disclosure and facts — is unchanged).
- **F-WE-a-7 — DOC-24 is not merged.** `ARC-84 … ARC-88` exist only in #175. WE-a's implementation base is
  after #175; this design cites `ARC-88` by id.
- **F-WE-a-8 — a third SplitMix64 copy.** `paced.rs` and weather's `draw.rs` each carry the mixer; DL-a moves the
  paced copy into `cognition/decision`, which a System Pack may not depend on. WE-a restates it a third time,
  pinned to the same reference vector, and routes extraction into a shared engine-neutral crate as a follow-up
  (QWE-8). Rule 11 (abstraction after the repeated concept) argues for extraction now; rule 5 (no edit to
  unrelated crates) and the open DL-a lane argue for later.

## 4. Design overview

```text
                    configure/happenings.yaml (content)        external generator packs (code, ARC-62)
                    seed · kinds · calendar · random ·          HappeningGenerator::drafts(&WorldRead, &DraftAsk)
                    limits · generators: [ids]                         │
                                │                                      │
calendar ── day-began ──► happenings: the daily pass ◄─────────────────┘
                                │   1 drafts   = calendar entries ∪ random entries ∪ selected generators
                                │   2 admit    = the host: catalog, place, window, duplicates, limits
                                │   3 state    = happening-announced (admitted) / happening-withheld (refused)
                                ▼
                         one `happening` Process each:  announced ──wake at start──► running ──wake at end──► ended
                                │ facts: happening-announced · happening-began · happening-ended
                                ▼
            other Systems react in their own reductions, from those facts, under their own configuration:
            economy  price_modifiers → prices-adjusted / prices-restored → its own Shop
            (later)  inventory/employment stock · schedule labels · motivated considerations · WE-b director
```

`happenings` is to world events what `weather` is to the sky: a System Pack with a content seed, a calendar
dependency, counter-based draws, Process state folded from its own facts, disclosure on the observer's place,
and no action anybody can take (WE-b adds the first one).

## 5. The `happenings` System Pack

### 5.1 Configuration: `configure/happenings.yaml`

A plain `ARC-61` `PackConfiguration` (`mineworld_sdk::configures!()`), decoded straight from the YAML stream
into the pack's types, so every refusal names the file, its line and column (`DEP-10`). `deny_unknown_fields`
throughout.

```yaml
seed: 7                              # u64; content, as weather's (F-WE-a-1)

kinds:                               # the kind catalog: what may happen, and where
  - id: market-day                   # HappeningKindId: system-id grammar, ≤ 32 bytes, unique
    title: Saturday market           # optional, ≤ 64 bytes UTF-8, no control characters; shown, never parsed
    places: [street]                 # place keys where it may happen (≥ 1, ≤ 16), checked by the loader
    hours: "08:00-14:00"             # local HH:MM-HH:MM, from < until, same day, minute resolution
    days: 1                          # 1 … 14: a multi-day happening runs from day 1's from to day N's until
    announce_days: 0                 # 0 … 30: announced this many days before it begins (0 = at its midnight)
    audience: public                 # public | place: began/ended heard everywhere or at its place
  - { id: festival, title: Harvest festival, places: [park], hours: "16:00-22:00", announce_days: 7 }
  - { id: street-musician, places: [street, park], hours: "11:00-13:00", audience: place }

calendar:                            # bundled generator `calendar`: pure functions of the date
  - { kind: market-day, place: street, weekdays: [saturday] }
  - { kind: festival,   place: park,   date: "10-31" }          # yearly; "02-29" fires only in leap years
  - { kind: market-day, place: street, monthday: 1 }            # exactly one of weekdays | date | monthday

random:                              # bundled generator `random`: seeded integer draws
  - { kind: street-musician, place: street, per_mille_per_day: 150 }
  - { kind: street-musician, place: park, per_mille_per_day: 60, weekdays: [saturday, sunday], months: [5, 6, 7, 8, 9] }

limits:                              # the host's own caps (§5.3); defaults shown
  per_day: 3                         # 1 … 16: happenings beginning on one day, world-wide
  per_place_running: 1               # 1 … 4: happenings overlapping in time at one place

generators: []                       # external generators this world selects, by their pack's system id (§5.5)
```

**Typed model (Rust, `src/configuration.rs`, `src/kind.rs`, `src/entry.rs`):**

```text
HappeningsConfiguration { seed: u64, kinds: KindCatalog, calendar: Vec<CalendarEntry>,
                          random: Vec<RandomEntry>, limits: Limits, generators: Vec<SystemId> }
KindCatalog             BTreeMap<HappeningKindId, HappeningKind>; 1 … 64 kinds; duplicate id refused
HappeningKindId         newtype over a slug (system-id grammar), ≤ 32 bytes
HappeningKind           { title: Option<Title>, places: PlaceSet<EntityKey>, hours: Hours, days: Days,
                          announce_days: AnnounceDays, audience: Audience }
Hours                   { from: Minute, until: Minute }, 0 ≤ from < until ≤ 1 440 (24:00 allowed as until)
Days                    1 … 14            AnnounceDays   0 … 30            Audience  Public | Place
CalendarEntry           { kind, place: EntityKey, when: Recurrence }
Recurrence              Weekdays(WeekdaySet) | Yearly { month: 1…12, day: 1…31, valid for the month } |
                        Monthly { day: 1…28 }       (29 … 31 refused: "use a date entry")
RandomEntry             { kind, place: EntityKey, per_mille_per_day: PerMille (0 … 1 000),
                          weekdays: Option<WeekdaySet>, months: Option<MonthSet> }
Limits                  { per_day: 1 … 16 (3), per_place_running: 1 … 4 (1) }
WeekdaySet / MonthSet   bit sets decoded from names / numbers; empty or repeated refused
```

**Refused at load, by name** (in addition to `ARC-61` item 5's generic refusals):

| Case | Where | Message names |
| --- | --- | --- |
| an unknown key, a value out of bounds, a malformed `hours` or `date`, `from ≥ until`, two of `weekdays`/`date`/`monthday` or none | decode | the key, line and column |
| a duplicate kind id; an entry naming an undeclared kind; an entry's `place` not in its kind's `places` | decode (`TryFrom` on the raw file) | the kind / entry index |
| a place key that is no Place | `references()` → loader | the key, the file |
| two random entries with the same `(kind, place)` (their stable draw key would collide) | decode | both indices |
| a `generators` id listed twice | decode | the id |
| a `generators` id that is not a registered generator of this build, or whose pack the world does not enable | `seed()` (registration happens in `compose`, before assembly) | the id, "not a generator of this build" / "not enabled in this world" |
| `happenings` enabled without `calendar` | kernel registry (`depending_on`) | `calendar` |

`requires()` returns nothing (calendar is a system dependency already); `attachments()` none.

**Seeding.** `seed()` resolves place keys to `PlaceId`s through `Seeding::resolve` and states one genesis fact,
`happenings-configured`, `Visibility::SystemInternal`, no subjects (`ARC-61` item 8), carrying the resolved
configuration with places as `PlaceId`. Drift (an edited file) is refused at resume by `ARC-61` item 7 with no
new mechanism.

### 5.2 System declaration

```text
system id     happenings                       SystemVersion 1
depends on    presence (disclosure), calendar (days; INV-TW-10's direction: calendar never knows happenings)
owns          two declared, never-carried records: happenings-here, happenings-announced (§5.7)
processes     almanac (one; the generator's state)  ·  happening (one per announced happening)
emits         happenings-configured · happening-announced · happening-began · happening-ended ·
              happening-withheld
subscribes    calendar's day-began (decoded through mineworld-calendar's type) and its own five facts
provides      nothing in WE-a (WE-b adds propose-happening)
biographical  none (a happening is not something a person did)
```

Cargo dependencies: `mineworld-authoring`, `mineworld-calendar` (path), `mineworld-contracts`,
`mineworld-kernel`, `mineworld-presence`, `mineworld-sdk`, `serde`, `serde_json`; dev: `mineworld-persistence`,
`mineworld-test-support`, `mineworld-worldpack`, `serde-saphyr`. No new third-party crate.

### 5.3 The daily pass: drafts, admission, limits

**Trigger.** Calendar's `day-began` for day index `d = day_start ÷ 86 400`. Reaction order inside the
reaction is fixed; the pass is a pure function of (configuration, `d`, the calendar date, the open happenings
in the almanac's state, and, for external generators, `&WorldRead`).

**Look-ahead with announcement.** Each draft source evaluates its entries for **one target day per entry**:
`t = d + announce_days(kind)`. So a festival announced 7 days ahead is evaluated, admitted and announced at the
midnight a week before it. **First pass catch-up:** on the first `day-began` after `happenings-configured`, each
entry is evaluated for every `t ∈ [d, d + announce_days(kind)]`, so a festival falling inside the first week is
still announced (late) rather than lost. The almanac records that the first pass ran (`started: true`), so
catch-up happens once per world, including across resume (it is a fold of a fact, §5.4).

**Bundled generator `calendar`** — for an entry and target day `t` with date `D = from_days(epoch_days + t)`:
`Weekdays(s)` fires iff `weekday(D) ∈ s`; `Yearly{m, day}` iff `(month(D), day(D)) = (m, day)`;
`Monthly{day}` iff `day(D) = day`. The date is computed from `day-began`'s date plus `t − d` days through
`CalendarDate::from_days`, never from the host.

**Bundled generator `random`** — an entry fires on `t` iff its optional `weekdays`/`months` admit `D` and

```text
key(entry)   = FNV-1a 64 over  "random" 0x00 kind-id 0x00 place-key        (stable; reordering moves nothing)
roll(entry,t)= permille( mix( mix( mix(seed, t as u64), key(entry) ), DRAW_FIRES ) )   ∈ 0 … 999
fires        ⇔ roll < per_mille_per_day
```

`mix` and `permille` restate weather's `draw.rs` exactly (SplitMix64 finalizer; multiply-shift to 0 … 999),
pinned by the same reference vector test (F-WE-a-8). `DRAW_FIRES = 0`; later draws take new indices. No RNG
state exists anywhere, so a resumed world draws as an uninterrupted one by construction.

**Draft.** Every source produces `HappeningDraft { kind, place: PlaceId, day: t }`; hours, duration and
audience come from the kind, so a generator cannot invent them.

**Admission (the host, `src/host.rs`, `admit`).** Drafts are ordered deterministically — source order
`calendar`, then `random`, then external generators by ascending system id; within a source, entry order (or
the generator's returned order) — and each is admitted or withheld in that order against the almanac's open
happenings plus those admitted earlier in the same pass:

| Check, in order | Withheld reason (`WithheldReason`) |
| --- | --- |
| the kind is in the catalog | `UnknownKind` |
| the place is one of the kind's `places` | `PlaceNotAdmitted` |
| `d ≤ t ≤ d + announce_days(kind)` (a generator may only schedule inside its kind's horizon; never the past) | `OutsideWindow` |
| no admitted or open happening has the same `(kind, place, start)` | `Duplicate` |
| fewer than `limits.per_day` happenings begin on day `t` | `OverDailyLimit` |
| fewer than `limits.per_place_running` happenings at `place` overlap `[start, end)` | `PlaceBusy` |

Calendar entries for the bundled sources are validated at load, so for them only the last three can fire;
external drafts can fail any. Each admitted draft yields `happening-announced`; each withheld one yields
`happening-withheld` (QWE-7), `SystemInternal`, no subjects, so an author can see why "the festival never
happened" (`INV-15`) without anybody perceiving it. Withheld facts per day are bounded by the number of
entries plus each external generator's draft cap (`MAX_DRAFTS_PER_GENERATOR = 16`, drafts beyond it withheld
as `OverGeneratorCap`, counted in one fact).

**Why at announcement time.** All decisions are taken when a happening is announced, never when it begins, so a
happening that was announced always begins and ends; there is no "cancelled" state to model in WE-a.

### 5.4 Processes and facts

**`almanac` Process** (one per world, uninterruptible, no place, no expected end): started in the reaction to
`happenings-configured`. State `AlmanacState { configured: HappeningsConfigured, started: bool, open:
Vec<HappeningRef> }` — the fold of `happenings-configured`, the first `happening-announced` (sets `started`),
and every announced/ended happening (adds/removes from `open`). `open` is bounded: ≤ `per_day × (31 + 14)`
entries (≤ 720 at the maximum limits; ≤ 135 at the defaults). Snapshot budget: ≤ 16 KB at the defaults,
pinned by a test (weather's `the_climate_state_stays_within_its_snapshot_budget` precedent).

**`happening` Process** (one per admitted draft, uninterruptible, `at_place(place)`): started in the reaction to
`happening-announced`, `ending_at(start)` (or, for a draft whose start is the current instant's midnight with
`hours.from = 00:00`, the reaction states `happening-began` immediately rather than scheduling a wake at a
non-future instant). State `HappeningState { happening: HappeningRef, until: WorldTime, phase: Announced |
Running }`.

```text
wake at start  → state happening-began   (react: phase Running, reschedule to `until`)
wake at until  → state happening-ended   (react: end_process, remove from almanac.open)
```

**Identity.** `HappeningRef { kind: HappeningKindId, place: PlaceId, start: WorldTime }`, unique by the
`Duplicate` check. Facts carry the ref, never a `ProcessId`, so a reacting pack keys its own state by a value it
can read from any of the three facts.

**Facts** (`src/event.rs`; no public constructors; JSON payloads with this pack's codec):

| Fact | Payload | Visibility | Subjects / place | When |
| --- | --- | --- | --- | --- |
| `happenings-configured` | the resolved configuration | `SystemInternal` | none | genesis |
| `happening-announced` | `{ happening, until, title, source }`, `source: Calendar \| Random \| Generator(SystemId)` | `Public` (an announcement is news) | about the place; `at_place(place)` | the pass |
| `happening-began` | `{ happening, until }` | `Public` or `Place(place)` per the kind's `audience` | about the place; `at_place` | its start |
| `happening-ended` | `{ happening }` | as `happening-began` | about the place; `at_place` | its end |
| `happening-withheld` | `{ kind, place, day, reason, source }` | `SystemInternal` | none | the pass |

None is biographical (`SystemPack::BIOGRAPHICAL` empty): a market day is not something a person did, and
`ARC-29` biographies stay unchanged for a world that opts in.

### 5.5 User-written generators: the `HappeningGenerator` catalog (`ARC-62`)

Three ways to make a world evolve, from least to most code:

| Route | Who writes it | Carrier | WE-a? |
| --- | --- | --- | --- |
| New **kinds** and schedules | a world author | content: `configure/happenings.yaml` | yes |
| A new **generator** (deterministic code deciding *when*: weather-driven, population-driven, a fixed storyline) | a pack author | a System Pack implementing `HappeningGenerator`, listed on the catalog line | yes — the trait, registration, selection and admission; no external generator ships |
| **Proposals** from outside the world (an LLM director, a scripted storyline seat) | a controller author | a Controller Pack submitting `propose-happening` | WE-b |

```rust
/// A source of happening drafts, owned by `happenings` and implemented by other System Packs (ARC-62).
pub trait HappeningGenerator: Send + Sync {
    /// The implementing pack's system id: the name a world selects in `generators:`; generators are
    /// asked in ascending order of it.
    fn generator_of(&self) -> SystemId;
    /// The drafts for `ask`. Pure: reads only `world` and `ask`, keeps nothing, returns nothing where its
    /// own pack's state is absent. At most MAX_DRAFTS_PER_GENERATOR are considered.
    fn drafts(&self, world: &WorldRead<'_>, ask: &DraftAsk<'_>) -> Vec<HappeningDraft>;
}

/// What a generator is told: the day being opened and the catalog it must draft within.
pub struct DraftAsk<'a> {
    pub day: DayIndex,                // d
    pub date: CalendarDate,           // d's local date (calendar's)
    pub first_pass: bool,             // the catch-up pass (§5.3)
    pub catalog: &'a KindCatalog,     // kinds, places, horizons
    draws: Draws,                     // private: seed + d + generator id
}
impl DraftAsk<'_> {
    /// Draw `index` for target day `t`, per mille: counter-based over (seed, t, generator id, index),
    /// so a generator never needs, or keeps, an RNG.
    pub fn permille(&self, t: DayIndex, index: u64) -> u16;
}
```

- **Two real implementations earn the trait** (rule 11): the bundled `calendar` and `random` generators
  implement it internally and are called directly, not registered; the catalog reuses the same trait for
  external packs.
- **Registration** (`src/catalog.rs`): `register_generators(Vec<Box<dyn HappeningGenerator>>)` and
  `registered_generators() -> Option<Vec<SystemId>>`, copied in shape from `register_wayfinders` (sorted by id,
  duplicate id panics, a different list panics naming both, the same list again is a no-op).
- **The installed set** gains `extension mineworld_happenings::HappeningGenerator =>
  mineworld_happenings::register_generators: [];` — empty in WE-a. A user's generator pack is installed by
  `ARC-33`'s two lines plus its type on this line (`ARC-62` item 6), with no edit to `happenings`.
- **Selection.** A world lists the generators it uses in `generators:`; an unselected registered generator is
  never asked, so installing a generator pack changes no world that does not select it (INV-WE-1 at the
  generator level). Selection is checked at `seed()` (§5.1).
- **Parameters.** A generator's parameters are its own pack's `configure/<its id>.yaml` (`ARC-61`), typed by its
  own type and read from its own state in `world` — never an untyped blob inside `happenings.yaml`.
- **The host is `happenings`.** Every external draft passes `admit` (§5.3); a generator cannot exceed a limit,
  invent hours, or schedule the past.

### 5.6 What WE-b will reuse (forward contract, not implemented here)

WE-b's `propose-happening { kind, place, day, text ≤ 240 B }` validates by building a `HappeningDraft` and
calling the same `admit` against the same almanac state, mapping `WithheldReason` to typed `Rejection`s, and adds
only what proposals need: `limits.proposals_per_actor_per_day` and an optional kind field `proposable: bool`
(default `false`, so no WE-a world becomes proposable by accident). Both are additive keys with defaults, so a
WE-a configuration stays valid. Nothing in WE-a names a director, an Organization seat, or a model.

### 5.7 Disclosure

Two declared records, carried by no entity, computed from the Processes (calendar's precedent), disclosed
**about the place the observer is in** and to nobody elsewhere:

- `happenings-here`: the happenings running at this place now — `[{ happening, title, until }]`, ordered by
  start then kind.
- `happenings-announced`: the announced, not yet begun happenings anywhere in the world (public news) —
  bounded by the almanac's `open` list, ordered by start then place then kind.

An observer in no place gets neither. Neither carries any state that a fact did not already make public.

## 6. How other Systems react: events, never writes

### 6.1 The rule

`happenings` states facts about happenings and nothing else. A System that wants a happening to change its own
state subscribes to `happening-began` / `happening-ended`, decodes them through `mineworld-happenings`' published
types (a Cargo dependency, **no** system dependency — economy's `wage-due` precedent, `ARC-28`), and in its own
reaction states **its own fact**, which it then reduces into its own component. Each such reaction is the
reacting pack's configuration, opt-in, and absent by default.

### 6.2 The worked example: `economy` price modifiers

```yaml
# configure/economy.yaml (new; optional) — economy's first world configuration (ARC-61)
price_modifiers:
  - { during: market-day, shop: store, permille: 900 }    # 10 % off at the corner store on market days
```

| Element | Design |
| --- | --- |
| Carrier | `economy` gains `impl PackConfiguration` and `configures!()` beside its existing `owns_section!()` (§3.1 shows they coexist). `Configuration = EconomyConfiguration { price_modifiers: Vec<PriceModifier> }`, ≤ 32 entries. |
| `PriceModifier` | `{ during: HappeningKindId, shop: EntityKey (a Place carrying a shop), permille: 100 … 10 000 }`; `(during, shop)` unique. |
| Refusals | unknown key, out-of-bound `permille`, a `shop` that is no Place (`references()`); a `shop` place with no shop is refused at `seed()` once shops are known (sections are seeded after configuration, so this check runs in the reaction to `shop-opened` instead and fails genesis by name — decided in C4 by audit); `requires()` = `[happenings]` whenever the list is non-empty (INV-WE-4). |
| Genesis fact | `economy-configured`, `SystemInternal`, no subjects — the drift check covers it. A world with no `configure/economy.yaml` states none (byte identity). |
| Reaction | On `happening-began` whose kind matches a modifier for a shop: state `prices-adjusted { place, happening, permille }`, `Public`, at the shop's place, caused by the `happening-began`. On `happening-ended`: `prices-restored { place, happening }`. |
| Reduction | `Shop` gains `adjustments: Vec<Adjustment { happening: HappeningRef, permille }>`, serialized with `skip_serializing_if = "Vec::is_empty"` so a shop never adjusted encodes exactly as today. The effective price of a kind is `base`, then for each adjustment in `happening` order `p ← max(1, (p × permille + 500) ÷ 1 000)` — integers, deterministic. |
| Use | `buy`'s validation, its payment and the shop listing's disclosure all read the effective price through one function, `Shop::effective_price(item)`. |
| Version | `economy`'s `SystemVersion` 1 → 2 (its declaration grows: one configuration, two facts emitted, two subscriptions). Saves of economy worlds written before C4 are refused by name (`ARC-25`, as every declaration change). |
| What economy does **not** learn | Whether a happening is a "market"; it matches a configured kind id and nothing else. |

Removing `happenings` from a world whose economy names `market-day` is refused ("economy's configuration
requires happenings"); removing both returns the world to its pre-WE-a behaviour. A kind id in `during` that the
world's `happenings.yaml` does not declare cannot be cross-checked by economy at load (packs do not read each
other's configuration); it never matches. R-WE-a-4 records this; a `mineworld happenings` style inspector is a
later tool.

### 6.3 Other reactions, designed but not built

- **Stock.** Inventory owns holdings; restock is employment's production. A "market day brings extra bread" rule
  is employment's (or a later supply pack's) reaction stating inventory's fact through its checked
  constructor — same pattern, later PR.
- **Schedule.** `schedule` could switch a person's agenda label to `festival` for a happening's span, from its own
  section; schedule has no configuration today. Later PR.
- **Decisions.** DL-b's `motivated` model may score "go to where a happening is" from `happenings-here` /
  `happenings-announced`; a controller reads disclosures, never `happenings`' state.

## 8. Determinism, persistence, replay and platforms

- **Replay (`ARC-25`).** The pass, every wake and every reaction re-execute from the journal; nothing reads a
  host clock, an environment variable or a file at run time (the configuration is a genesis fact).
- **Kill and resume.** All state is Process state folded from facts; a resumed world continues the same
  happenings and the same draws. Tested mid-happening and across an announcement horizon.
- **Re-running from content (`AC-12`).** Same World Pack, same code → same `happening-*` facts, independent of
  `--seed` (that seeds controllers only). A test runs two different controller seeds and asserts identical
  `happening-*` facts in a world whose economy is unconfigured.
- **Platforms.** Integers only; `BTreeMap`/sorted `Vec` iteration only; FNV-1a and SplitMix64 on `u64` with
  wrapping arithmetic — the same bits everywhere. Covered by `cargo test` on `test` (Linux), `test-windows`,
  `test-macos`, and, with C5, by AC-8's four-platform comparison of Market Town.
