## ARC-171 — No prop moves unless the world moves it

**Date** 2026-10-21 · **Status** accepted (S33-e frozen by the operator 2026-10-19; implemented in PR S33-e1) ·
**Relates to** `ARC-177`, `ARC-178`, `ARC-144` (the depiction seam), step-33 I-S33-5 · **Design**
`.structured-coding/plans/mvp0/pr-s33e-pier-halt.md` §§5.5, 5.6 (X-7)

**Problem.** A client can make a world look busier than it is: a rowing boat crossing the lake, a train pulling
in, a ferry at the pier. None of these exists in the world unless a System runs a `Process` that moves it and
discloses it. A boat that drifts because a depiction tweened it tells the player that someone is rowing, which the
world never said. Step-33 names the rule ("nothing moves that the world does not move") but no file held it.

**Choice.**

1. Presentation may **idle** — water's ripples, leaves and grass in the wind, shader time — but never shows a
   behaviour the world does not have. A landmark's parts, a moored craft, a train, a ferry and every other prop a
   depiction draws are static meshes: no `AnimationPlayer`, no `Tween`, no per-frame transform write.
2. Something that moves in the world moves in the client only because the server discloses it (a person's
   position, a `Process`'s state), through the client's ordinary observation path.
3. The rule is held structurally (check (e) of `tests/acceptance/tests/client_rules.rs`): no script that draws a
   depiction (`clients/3d-spike/scripts/depictions/**`) creates a `Tween` or an `AnimationPlayer`, or defines a
   per-frame callback (`_process`, `_physics_process`), naming the file and line. Shaders are not scripts and
   are not scanned: idling is theirs.

**Consequences.** Lakeside's moored boats are static (S33-e §5.5); the halt draws no train (S29 §5.2). A world
that wants a moving boat writes a System and a `Process`, and the client draws what it discloses.
