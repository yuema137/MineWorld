## ARC-115 — `notices`: public, time-limited notices on declared topics, delivered to subscribers, expiring lazily

**Date** 2026-10-18 · **Status** accepted (step-31 approved 2026-10-15; S31-b PR design frozen by the operator 2026-10-18, Q-S31b-1 … 4 as recommended); implemented by S31-b · **Approved by** the operator, directly in the primary session · **Relates to** `ARC-26`, `ARC-31`, `ARC-33`, `ARC-34`, `ARC-43`, `ARC-61`, `ARC-90`, `ARC-112`, `ARC-124` · **Design** `.structured-coding/plans/mvp0/step-31-wealth-prices.md` §8; `.structured-coding/plans/mvp0/pr-s31b-notices.md`

**Problem.** The operator asked (2026-10-15) that "time-sensitive public information can be sent to other NPCs' inboxes, and each NPC can have an attribute for subscribing to public information". A price clerk that publishes suggested prices needs such a channel, and its backend may be a deterministic algorithm or a language model, so whatever publishes must be validated alike. Before this record, a fact reached either the people in a place, the participants, the people named, or everybody. Nothing reached "the people who asked for it".

**Options considered.**

| Option | Verdict |
| --- | --- |
| A message broker (NATS, MQTT, Redis pub/sub) or an in-process bus crate | Declined: delivery is perception, which presence already owns (`ARC-43`) and the event log already persists. A broker would hold world state outside the log and outside the server-authoritative path (`CLAUDE.md` §4 rules 3, 16) |
| WE-a's `Public` announcements | Declined: a public fact reaches everybody, so "subscribe" would mean nothing |
| **One System Pack that owns topics, subscriptions and notices; a notice's audience is the subscribers; expiry is computed, not stated** | **Chosen** |

**Choice.**

1. **Topics are world configuration.** `configure/notices.yaml` declares 1 … 32 topics. Each has a body kind (`prices` or `text`), 1 … 16 named publishers, a validity range (`valid_for: { min, max }`, 1 minute … 30 days) and `per_day`. The configuration is stated as one `notices-configured` fact, `SystemInternal`, and kept in one never-woken `notices-board` Process with the notice counter and the newest notice per (topic, publisher).
2. **Subscriptions are a Person's component, `Subscriptions`, owned by `notices`.** They are seeded at genesis from the person's `notices:` section, or else from the configuration's `defaults.by_tag`; an authored section replaces the defaults, and `subscribe: []` means none. The genesis fact `subscriptions-seeded` is `SystemInternal` (Q-S31b-2), so no inbox or memory starts with a fact nobody witnessed. After genesis, only the person's own `subscribe` and `unsubscribe` change the set, each a fact visible to that person only.
3. **Actions.** `publish-notice { topic, body, valid_for }`, `subscribe { topic }` and `unsubscribe { topic }`, each with no spatial requirement: a bulletin is sent, like a message. Each is offered **incomplete** and once (Q-S31a-3), so a generic controller never publishes or subscribes at random; only a model that chooses to can.
4. **The audience is the subscribers.** `notice-published` is stated with `Visibility::Entities` of the topic's subscribers at that instant plus the publisher. Presence's audience rule (`ARC-43`) then puts it into exactly those perceived streams: an NPC's observation, an agent's inbox, and each subscriber's memory. A person who subscribes later does not receive the old notice, but sees it on the board while it is current.
5. **Lazy expiry.** A notice is current while `issued_at ≤ now < valid_until` and no later notice from the same publisher on the same topic replaces it. The `notice-board` record lists, to each person only, the current notices of the topics it subscribes to or publishes, computed from world time at disclosure. An expired notice leaves the board exactly at `valid_until`, with no wake and no fact; the inbox and memory keep it.
6. **Refusals, by name, one function for offer and dispatch.** `publish-notice` checks, in this fixed order: not a living person or no configuration (`NoSupportedInteraction`), `unknown-topic`, not a publisher (`PermissionDenied`), `body-mismatch`, `body-too-large` (> 32 lines, > 280 bytes), `body-invalid` (a line naming a non-Item, a price of 0 or above 10^12, a `basis` of 0, items not strictly ascending; empty text or a control character), `validity-out-of-range`, `over-daily-limit`. `subscribe` and `unsubscribe` add `already-subscribed` and `not-subscribed`. A payload that does not decode is `PreconditionFailed`.
7. **`per_day` is a rolling window** (Q-S31b-4): at most `per_day` notices by one publisher on one topic in any 86 400 seconds of world time. The kernel has no day, and `notices` depends on no other System, so it cannot read `calendar`'s date.

**Consequences.**

- `notices` depends on no System. It uses the `mineworld-presence` crate only for `PerceptionProvider`, like `naming`.
- The body kinds are a closed catalog in code. Adding one (`departures`, for S21) is one variant plus its renderer, reviewed as a vocabulary change. `notices` does not know what a price means: a price line is an item and an amount the publisher claims, with `basis` its own count of observations. Its bound `NOTICE_PRICE_MAX = 10^12` equals economy's `PRICE_MAX` by design (`ARC-112`).
- Duration strings (`"6h"`, `"7d"`) are parsed by the pack's own ten-line type. `humantime` and `duration-str` were declined: they accept forms (`1h 30m`, fractional units) the reference would then have to document and bound.
- Memory renders a received notice as "<publisher> posted <topic> (valid until Day n HH:MM): <summary>". The `(expired)` marker at recall needs an S28 record field and is S28's to add (Q-S31b-3).
- Until S30-c's attribute owner crate merges, the subscription "attribute" is this pack's own section and defaults; the adoption is recorded under `ARC-124`.

**Revisit** when a System, not a person, must publish (`weather-warnings`), when a body kind is needed beyond `prices` and `text`, or when an audience grows past S28-g's scale gate.

## ARC-115 note — the `topics` record (2026-10-26, S31-b2)

Q-S31g-3 (ruled yes, 2026-10-20) and R-S31b-g-2: `notices` discloses a `topics` record, so a person can see which topics the world has before subscribing. `TopicsRecord { topics: [TopicLine] }`, component type `topics`, owned by `notices`, declared and carried by no entity (like `notice-board`), computed from the board and the person's `Subscriptions` at each read; no fact. Each `TopicLine` is `{ topic, body, valid_min, valid_max, per_day, may_publish, subscribed }`, every declared topic in id order; `valid_min` and `valid_max` are seconds, named as in `notices-configured` (SD-b2-4); the publisher list is not disclosed. **Disclosed to every living Person about itself only, in a configured world** (Q-S31b2-5): `may_publish` and `subscribed` are about the observer, and subscriptions are private (I-S31-9). A world without `configure/notices.yaml` has no record. The agent adapter's `View.topics` line (R-S31g-b2-1) and the clients' topics panel (R-S31e-b2-1) read it; S31-g and S31-e merged before this PR, so both are follow-ups (`pr-s31b2-notices-attributes.md` §14.1).
