## ARC-144 — The 3D client draws a world through one depiction per world key, bound by tag

**Date** 2026-10-19 · **Status** accepted (PR S33-c design frozen 2026-10-18); implemented by S33-c · **Approved by** the operator's freeze of `pr-s33c-world-seam.md` (2026-10-18) and rulings Q-S33-3, Q-S33-4 and Q-S33c-1 · **Relates to** `ARC-45`, `ARC-102`…`ARC-104`, `ARC-146`, [`MODULE_SPEC.md`](../MODULE_SPEC.md) §6 · **Design** `.structured-coding/plans/mvp0/pr-s33c-world-seam.md` §§5.1–5.6; `step-33-lakeside-3d.md` §4.8 (SD-S33-6)

**Problem.** The 3D slice drew one world only. Its scene was Social Café's street, its far field was loaded under a constant key (`social-cafe`), its spawn, viewpoints and door table were Social Café constants spread over five files, and its binding anchored only on a place tagged `cafe`. So `--world=lakeside` hosted Lakeside on the server and still drew the café street: Lakeside's people, whose looks the world discloses, never appeared in 3D. A second world could only be added by editing the café's code.

**Options considered.**

| Option | Verdict |
| --- | --- |
| (a) A hand-written table from world key to builder script in the client | Declined: it is a list of world keys in the client, the seed of the place-key list 16c's SC-4 forbids, and it is edited for every world |
| (b) Branches on the world key inside the existing scene code | Declined: world-specific code in the shared mechanism; the next world would edit it again |
| (c) **One depiction interface, found by path convention from the world key, bound to disclosed places by tag set and doorway coincidence** | **Chosen** |

**Choice.** The 3D client selects a world by key (`--world-key=<key>`; offline with no `--server=`, `social-cafe`). The registry (`SliceWorlds`) finds the key's depiction at `res://scripts/depictions/<key>/depiction.gd`. A depiction (`SliceDepiction`) is a builder with one interface: `build(root, far_field, connected)`, `place_volumes()`, `depictions()` (what is drawn as which tagged place: `{tags, volume, drawn_as, door, origin}`), `doors()`, `spawn()`, `viewpoints()`, `sit_points()`. `SliceLayout` binds each disclosed place to a depiction entry by its disclosed tags and by doorway coincidence (16c's D-16c-3 rule generalised): the first observed place with a candidate entry anchors the scene, by a declared frame origin or by its door's in-point; the place its door opens onto is bound to the `STREET` entry; every other place binds to the drawn door its disclosed doorway lands on within `DOOR_MATCH`. An ambiguous or unmatched place is a reported miss, never a guess. The client names no place key: `client_rules.rs` check (d) refuses a place-key string literal in the 3D client and `clients/shared/`, except as the argument of `SliceDepiction.tag()`. Social Café is the first depiction, with no visual or behavioural change; a labelled Lakeside stub is the second (Q-S33c-1); the boxes, doors and volumes of a stub are built by a shared data-driven builder (`SliceBoxDepiction`), so a stub is a data table.

**Consequences.** `./mineworld-slice --world=<key>` hosts `worlds/<key>` on the same server path and draws it through its depiction. A world key without a depiction is refused by name (`ARC-146`). 16f keeps `SliceDepiction` as the boundary and changes only where depictions come from (a Presentation Pack, walls from disclosure; R-16f-c-1). S33-d replaces Lakeside's stub behind the same file and interface.

**Limitation accepted.** The depictions are still scripts in the client project, not data of a Presentation Pack; the lighting rig (VoxelGI, reflection probes) is still placed for the café's street in every world. Both are 16f's and S33-d's.

**Revisit** when 16f loads depictions from a Presentation Pack.
