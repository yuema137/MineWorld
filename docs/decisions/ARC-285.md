## ARC-285 — Item nourishment is the `needs` section on item files (`needs: { nourishment: … }`)

**Date** 2026-10-18 · **Status** accepted (design, step 35); to be implemented by PR N-b. The section's spelling follows Q-Nb-1 option (a) of N-b's PR design, **pending the operator's ruling** · **Approved by** the operator, in the primary session, 2026-10-18 (step 35 frozen; the generic-mechanism ruling below) · **Relates to** `ARC-31`, `ARC-36`, `ARC-37`, `ARC-71`, `ARC-284`, `MODULE_SPEC.md` §4.1 (sections) · **Design** `.structured-coding/plans/mvp0/step-35-needs-and-sleep.md` §§5.1, 5.3, 5.5, 7; N-b's PR design, Q-Nb-1

**Problem.** Eating soup should restore more hunger than eating an apple, and a cup of coffee none. The amount belongs with the item kind, because an author writes it once per kind. But the `item` pack owns the item file's `item:` section, and it must not learn what hunger is. And `consumption`, which offers `eat`, owns no state and is "the interaction, not a need". Step 35 first wrote the amount as a second top-level section, `nourishment:`. N-b's design found that a pack owns exactly one section name (`ARC-31`; `MODULE_SPEC.md` §4.1: "A pack owns one section"), so `needs` cannot own both `needs:` and `nourishment:`.

**Options considered.**

| Option | Verdict |
| --- | --- |
| (a) A field in `item:` (`item: { category: food, hunger: 600 }`) | Declined: `item` would learn about needs, and removing `needs` would leave a field nobody reads |
| (b) Restore by category (`food` restores a fixed amount) | Declined: step-24 §6.5 started there, but soup and an apple would nourish alike, and a world could not tune one kind |
| (c) A table of amounts in `configure/needs.yaml`, keyed by item | Declined: two places to keep in step when an author adds a kind; an Entity Pack's kinds could not carry their own amounts |
| (d) A second top-level section `nourishment:` owned by `needs` | Declined: it breaks the one-section-per-pack rule of `ARC-31` |
| (e) **The `needs` section itself, carried by people and items, with a different shape on each** (Q-Nb-1 (a)) | **Chosen**, pending the operator |

**Choice.** On an item file that declares a kind, the `needs` section is `needs: { nourishment: { hunger: <0 … 1 000> } }`. On a person file it holds the initial levels (`ARC-284`). The `needs` pack declares and decodes both forms, and `needs` alone reads the item form, when it reduces inventory's `items-consumed`: hunger falls by `nourishment.hunger` × count. An item kind without the section nourishes 0. The item form is disclosed to nobody. It is refused at load, by name and with line and column, when the world does not enable `needs` (`ARC-31` rule 6), when the world does not enable `consumption` (nothing could ever eat the item, `MODULE_SPEC.md` §4.1), when a value is out of bound (`hunger: 1 001`), when a key is unknown, and when a form is written on the wrong kind of file (levels on an item, `nourishment` on a person).

**The generic-mechanism ruling (operator, 2026-10-18).** No item is named in code. Market Town's menu values (soup 600, sandwich 650, bread 500, cake 400, croissant 350, apple 200, juice 100, milk 150, coffee 0, tea 0; step 35 §5.5, authored) are content in N-d's item files, and a second world sets its own.

**Consequences.** An Entity Pack's item files may carry the section, decoded with the requiring world's enabled systems like any section (`ARC-71`). Removing `needs` means removing its sections too, or the world is refused by name rather than silently keeping inert data. The item form is open to a later need (`thirst`) as a new optional key under `nourishment`, with its own bound. If the operator rules Q-Nb-1 otherwise, this record gets a dated note with the chosen spelling.

**Revisit** when a second need is restored by eating or drinking, or when an item's effect depends on more than its kind.

**Note, 2026-10-19 (PR N-b) — the spelling is ruled and implemented.** The operator ruled Q-Nb-1 option (a)
on 2026-10-18: `needs: { nourishment: { hunger: 600 } }` on an item file, one `needs:` section with a person
form and an item form, the `body:` precedent. Mixing the forms is refused at the section; a form on the other
kind of file is refused when seeded, with `needs-section-kind`. The item form requires `consumption` through
the generic `AuthoredSection::requires` (`ARC-31` note of 2026-10-19), refused as `SectionRequiresSystem`. The
amount becomes the `Nourishment` component on the item kind through `nourishment-assigned`, and is disclosed
only inside its holder's own `needs` record.
