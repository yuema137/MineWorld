## ARC-183 — The LM controller fills an incomplete offer through a typed filler from a closed registry

**Date** 2026-10-26 · **Status** accepted · **Approved by** the operator, 2026-10-20, primary session (Q-S31d-2 and Q-S31d-3 ruled as recommended) · **Amends** `ARC-72` (see its note) · **Relates to** `ARC-34`, `ARC-58`, `ARC-116`, `ARC-153` · **Design** `.structured-coding/plans/mvp0/pr-s31d-reporter-policies.md` §5.8

**Problem.** An LM seat may say something, attempt a numbered complete offer, or do nothing (`ARC-72`). An incomplete offer — `publish-notice`, economy's seller actions, haggling's proposals — carries no payload, so an LM seat could never take one: an LM price clerk could not post its bulletin. The LM also acts only when spoken to or when a known person arrives, so a clerk would never post on its own.

**Options considered.** (a) Let the model write a payload — rejected: the model would build requests (`ARC-72`). (b) A generic free-form act — rejected, as `ARC-153` rejected it for MCP (QS27-9). (c) **A closed registry of typed fillers, one per incomplete action type** — chosen.

**Choice.**

1. A **filler** is a pure part of the LM controller that knows one incomplete action type: when it is listed (the observation offers the action available, and the filler's own preconditions hold), the prompt section it shows (labels only, never an entity id), the JSON schema of the typed fields the model must answer with, the checks on those fields, and how the checked fields become the request payload. The registry is closed: a new incomplete action is one filler module and one registry line.
2. The model's answer gains the act `fill`, with `fill: { offer: "F<n>", <filler key>: <its fields> }`. A failed check is a named content failure; an F-number not listed is `unknown_fill`. The checked payload is submitted through `mineworld_sdk.offers.request`, so the observation must still offer the action, and the world judges the request.
3. **Nothing listed, nothing changes.** When no filler is listed, the prompt, the output schema, the parse, the validation, the request and the decision-log record are byte-identical to before, so every committed cassette keeps its key.
4. **The `due` trigger.** A filler may name perceived fact types (`due_events`); a seat whose newest observation lists that filler gets a `due` consult when such a fact is perceived. The first filler, `publish-notice`, names calendar's `day-began`: one consult per world day per clerk.
5. The first filler is `publish-notice` with a `prices` body: it shows the clerk's own `survey-book` (`ARC-116`) by kind names and seller names, checks every line (a kind shown, no kind twice, `1 ≤ price ≤ 10^12`, `1 ≤ basis ≤` the notes shown), and builds `{ topic, body: { prices }, valid_for }` with the topic and validity from operator configuration (`cognition.toml` `[fill.publish-notice]`), never from the model.

**Consequences.** The deterministic `price-reporter` and an LM clerk submit the same request shape, judged by the same `judge_publish`. Economy's seller actions and haggling's proposals follow as one filler each. An LM seat still never walks.
