## ARC-154 — Speed first: pull requests and main run `fast` only; the full matrix runs at milestones (amends `ARC-48` and `ARC-110`)

**Date** 2026-10-18 · **Status** accepted (operator policy, 2026-10-18); proposed in the PR "ci: fast only per PR and per merge; the full matrix at milestones"; in force at its merge · **Approved by** the operator, in the primary session, in four rulings of 2026-10-18 (quoted below), relayed by the coordinator; the details are the implementer's, within them · **Relates to** `ARC-48` and its notes of 2026-10-09 (13b, 13w, 13x), `ARC-83` (the nightly, unchanged), `ARC-110` (shards and gates), [`ENGINEERING_STANDARDS.md`](../ENGINEERING_STANDARDS.md) §§15–16 · **Design** `.structured-coding/plans/mvp0/pr-ci-milestone-runs.md`; `scripts/ci_changes.py`, `.github/workflows/ci.yml`

**Problem.** Before this record, every non-draft code PR and every push to `main` ran the whole matrix. That was about 13 jobs: three Linux test shards, four Windows shards, two macOS jobs, `platforms (windows-2025)`, `python` on Linux and Windows, and `removability`, at 45–60 min of wall time each. The CI service's runners were shared by many PRs at once.

**The operator's rulings, in order:**

1. "为了节省时间，我们尽量不要跑全量 ci，而是只跑必要的。只有到了一个新验收标准完成，我们再跑 ci" — run only what is needed; run the full CI when an acceptance criterion is completed.
2. "ci 资源有限，我们不应该给每个 pr 都跑，这样会造成大量重复。我们应该攒几个比较相关的，然后一起跑" — do not run CI for every PR; collect related PRs and run them together.
3. `removability` becomes a required status check on `main`.
4. The latest ruling, which supersedes the targeted per-PR runs and merge trains that rulings 1–2 had been drafted into: speed first. There are no per-PR test runs. The full, acceptance and integration tests run at milestones only, and their failures are fixed then, in one batch.

**Choice.** `scripts/ci_changes.py` puts every run into one **mode**, and every job of `ci.yml` reads it.

| Mode | When | What runs |
| --- | --- | --- |
| `docs` | every changed path is in `ARC-48`'s audited docs set (13x), unchanged | `fast` runs the `docs` layer |
| `deferred` | every other pull request, every push to `main`, and a dispatch without `milestone` | `fast` only: format, `cargo check`, clippy, `cargo deny`, the CI scripts' self-tests, and the Python static checks |
| `full` | a `workflow_dispatch` with the input `milestone: true`; a PR labelled `milestone`; a `scratch/**` push | every layer on every OS, as before this record. A milestone dispatch also runs the AC-8 legs and `ac8`, and so does a `-scenario` scratch branch |

1. **The required gates always report on a pull request.** These are `test`, `test-macos`, `test-windows`, and `removability`, which is required from ruling 3. They run on every non-draft PR and on every dispatch.
   - If `changes` failed, the gate is red.
   - If the mode is not `full`, the gate passes in seconds. Its job summary says "deferred to milestone (operator policy 2026-10-18)", or gives the documentation note.
   - Otherwise the gate is green only when every one of its shards is green, as under `ARC-110`.

   `removability` is one job: its first step decides, and its checkout and layer steps run only on a `full` run. Branch protection on 2026-10-18 requires `fast`, `test` and `test-macos`, and none of this needs a change to it.
2. **On a push to `main`** only `changes` and `fast` run, and the gates do not run at all. The nightly's flake sampler (`ci_nightly.py` `main_push_run`) reads the `test`, `test-macos` and `test-windows` jobs of `main`'s push run as samples. A gate that passed without its shards would be counted as a passing test sample, so the gate must not report there. A missing job gives no sample, and the nightly itself is unchanged (`ARC-83`).
3. **The milestone run.**
   - **When.** A lane completes an acceptance criterion, or a milestone handoff is about to happen.
   - **Who.** The coordinator (the primary session) dispatches `ci.yml` on `main` with `milestone: true`: `gh workflow run ci.yml --ref main -f milestone=true`. If the milestone's last change is still a PR, the coordinator labels that PR `milestone`.
   - **Failures.** They are fixed in one batch, as PRs that are themselves verified by the next milestone run.
   - **Labels.** `pull_request` also listens to `labeled` and `unlabeled`, so adding `milestone` re-runs the PR in full. Any other label re-runs `fast`.
4. **Fail closed, where it still matters.** A change set that cannot be computed (an empty diff, an unknown base, any `git` failure) is code, as under `ARC-48` 13x. It therefore runs `fast` and the gates, never the `docs` layer. No classification can make a milestone run smaller: a `full` run is every layer, whatever the diff.
5. **Unchanged:**
   - every layer's commands in `ci_layer.py`, and the `ARC-110` shard partition;
   - `ARC-48` 13x's documentation set;
   - the nightly (`ARC-83`);
   - scratch branches, which still run in full, with the far field by path, for mutation evidence (step-14 §9.0 R-4).
6. **Not adopted.** Two earlier designs were drafted in the same PR and then superseded by ruling 4 before they merged:
   - targeted per-PR runs, which would have tested the packages affected by the diff and their reverse dependencies, on Linux only;
   - merge trains of related PRs (`train/*` branches built by a helper script).

   A rehearsal on 2026-10-19 confirmed one fact for later use. When a PR whose branch merges several component heads is itself merged with a merge commit, GitHub marks each component PR as merged: #271 merged #269 and #270 into a throwaway base. The rehearsal branches are deleted.

**The trade-off, stated.**

- No merge is test-gated: not on any OS, not by the core suite, not by Python, removability or the far field. Only `fast`'s structural checks gate a merge.
- A break is found by the next nightly (`ARC-83`: parity-long, stability and repeat samples on `main`), or at the next milestone run. It is not found per PR or per merge.
- Between milestones, `main` can hold several breaks at once, and a milestone run may fail for more than one reason. Fixing them is that milestone's batch.
- A green `test`, `test-macos`, `test-windows` or `removability` on a PR now means "deferred", never "tested". The job summary says which.

**Consequences.**

- A PR's run is `changes`, `fast` and the four gates: about 10–15 minutes on Linux runners. A push to `main` runs `changes` and `fast`.
- The AC-8 legs no longer run on every push to `main`. They run at milestones and on `-scenario` scratch branches.
- **Required check change, after merge (the operator's, not this PR's).** `removability` joins `fast`, `test` and `test-macos`. The API takes `checks` objects. `strict` must be a boolean, which JSON input or `-F` gives; `-f` sends the string `"false"`.

  ```sh
  gh api -X PATCH repos/yuema137/MineWorld/branches/main/protection/required_status_checks --input - <<'JSON'
  {"strict": false, "checks": [{"context": "fast", "app_id": 15368}, {"context": "test", "app_id": 15368},
   {"context": "test-macos", "app_id": 15368}, {"context": "removability", "app_id": 15368}]}
  JSON
  ```

**Revisit** if milestone runs fail for so many reasons at once that the batch costs more than per-PR CI did, or if a break found by the nightly blocks other lanes for more than a day.
