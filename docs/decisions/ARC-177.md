## ARC-177 — A world's 3D look is a data file of its Presentation Pack, drawn by generic builders

**Date** 2026-10-21 · **Status** accepted (S33-d revision 2 frozen by the operator 2026-10-20, Q-S33d-3…6 as
recommended, relayed by the coordinator; implemented in PR S33-d) · **Approved by** the operator's ruling of
2026-10-20 (the S33 lane's Q4: "Lakeside's village is a data file read by generic builders, not GDScript
constants") and the lane-lead charter's rule of 2026-10-18 ("No world-specific hard-coding") · **Relates to**
`ARC-144`, `ARC-146` (the depiction seam, unchanged), `ARC-307` (furniture is the world's), `ARC-102` (the far
field's format, the pattern followed), `DEP-16` (YAML's JSON subset), `DEP-77`, `DEP-78`, `DEP-79`,
[`MODULE_SPEC.md`](../MODULE_SPEC.md) §6.1.2, [`clients/3d-spike/PRESENTATION.md`](../../clients/3d-spike/PRESENTATION.md)
§6 · **Design** `.structured-coding/plans/mvp0/pr-s33d-terrain-water-exterior.md` (revision 2) §5.0

**Problem.** Revision 1 of S33-d put Lakeside's heights, water line, quay, houses and woods into five GDScript
builders that would have been Lakeside's alone. A second lakeside town would have needed five new scripts, and a
moved cottage a code change. The operator's standing rule rejects a mechanism that only makes the default town
work.

**Choice.**

1. A 3D Presentation Pack may carry `depictions/<world-key>.yaml` (format 1, YAML's JSON subset): the world's
   street and place bindings by tag, spawn, terrain (regions, height profiles, splat layers), near water,
   edges (kerbs, quays, revetments, rails, low walls, gates), trails, building shells (massing, roofs,
   materials, openings), woods (species table, stands, single trees, air walls), scatter, light volumes and
   viewpoints. The folder is optional; a world drawn by a bespoke script has no file.
2. The 3D client reads it with `SliceDepictionFile` and draws it with `SliceDataDepiction` and the generic
   builders under `clients/3d-spike/scripts/depictions/data/`. No builder names a world, a place key, a tag
   or a species; every value that differs between worlds is a field of the file.
3. `mineworld packs validate` checks every depiction file of a pack (`mineworld_packages::depiction`): typed
   schema, unknown keys refused, eight codes in order — `DEPICTION_MALFORMED`, `_SCOPE_MISMATCH`, `_UNCITED`,
   `_OUT_OF_RANGE`, `_POLYGON`, `_REFERENCE`, `_DOOR`, `_ON_FLOOR`. The client refuses by the same names for
   what it checks (shape, scope, and the names only it knows: texture slugs, tree forms and cards) and trusts a
   validated pack for geometry (Q-S33d-4 (A)). A corpus test proves the two readers agree.
4. The server never reads the file. It holds no furniture (`ARC-307`: the schema has no field for a
   free-standing piece, and nothing it draws may stand on a place's floor except the shell that depicts that
   place) and no rule, capacity, passability or height the server sees.
5. A house's footprint is written twice — in the world's place file (the server's walls) and in the
   depiction file (the drawn walls) — and the geometry probe names any drift (Q-S33d-5 (A)). The second world
   of every acceptance criterion is the generated variant `lakeside-v7` (Q-S33d-6 (A)).

**Reuse.** Adopted: the JSON subset and Godot's `JSON` / `serde-saphyr` (already in the build); typed serde
with `deny_unknown_fields` (the far field's pattern); Godot's `Geometry2D` and `Curve` in the client.
Rejected, with reasons (facts read 2026-10-21; S33-d §15):

| Candidate | Fact | Verdict |
| --- | --- | --- |
| JSON Schema (`jsonschema` crate) | a new lockfile entry and a second validation style beside the far field's | rejected |
| `geo` crate (MIT OR Apache-2.0, 0.33.1) | the checks are two predicates (simple polygon; overlap with a rectangle) on ≤ 64 vertices; ≈ 60 lines of ours against a new crate tree | rejected; adopt if our polygon code passes 150 lines |
| ProtonScatter (MIT, Godot 4) | authored in the editor; whether it scatters at run time from data is not stated in its README (INCONCLUSIVE) | rejected: ours must be driven by a file the Rust validator also reads, seeded and equal on three OSes |
| Spatial Gardener (MIT, Godot ≥ 4.2) | an editor plugin for finite medium-sized scenes | rejected, same reason |
| Godot CSG | "mainly intended for prototyping"; "forcing too many objects in a single tree will eventually start affecting performance" (Godot docs, CSG) | rejected for shells |
| func_godot (MIT) | reads Quake/Valve `.map` brushes from TrenchBroom: hand-modelled geometry, not massing data a validator can range-check | rejected |
| Cyclops Level Builder (MIT) | "block in levels inside the Godot editor" | rejected (editor authoring) |

**Consequences.** A second town by a lake is a second data file; the builders do not change. Later PRs that
need a shape format 1 cannot say (S33-e's deck and track, 16f-d1's `models`) add an optional section through
their own design; every existing file stays valid.

**Revisit** when 16f lets a world exist with a data file and no script (the registry looks the file up
itself), and when a third world's depiction needs a field the format lacks.
