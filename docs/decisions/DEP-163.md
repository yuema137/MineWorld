## DEP-163 — cargo-nextest runs the `core` suite in CI

**Date** 2026-10-27 · **Status** accepted · **Approved by** operator ruling Q-3 of 2026-10-27 ("adopt cargo-nextest,
with a DEP record"), relayed by the primary session · **Relates to** `ARC-110` (the weighted shards), `ARC-154`
(milestone runs), `DEP-18` (the toolchain image) · **Design** `.structured-coding/plans/mvp0/pr-ci-test-economy.md`
§2.3, §5 P1

**Problem.** CI ran the `core` suite with `cargo test`. Three gaps followed from that runner. First, `cargo test`
writes no machine-readable per-test result, so the shard weights (`scripts/ci_shard.py` `WEIGHTS`) were
reconstructed by hand from log timestamps, and two heavy binaries were missing from the table. Second, a failing
test is found by scraping the log. Third, the per-PR `impact` job (Q-1) needs to select tests by an expression over
packages, binaries and test names, which `cargo test` cannot do in one command.

**Options compared.**

| Option | What it gives | Verdict |
| --- | --- | --- |
| **cargo-nextest** (Apache-2.0 OR MIT; Linux, macOS, Windows; maintained since 2022) | JUnit with each test's own time; filtersets (`package()`, `binary()`, `test()`, `rdeps()`); no fail-fast per profile; test groups for tests that must run alone; archives for build-once, run-many | **Adopt.** It runs our tests unchanged and stays a runner: world state, ownership and CI policy remain ours. |
| keep `cargo test`, parse its log | no new tool | Rejected: the weights stay hand-made, and selection by expression needs a second tool anyway. |
| `cargo test -- -Z unstable-options --format json` | per-test JSON | Rejected: needs a nightly compiler; the workspace pins stable 1.97.1. |

**Choice.**

- Version **0.9.148** (released 2026-10-08), pinned in two places that must agree: the `Dockerfile` toolchain stage
  (`cargo install --locked cargo-nextest@0.9.148`, the `cargo-deny` pattern) and `.github/actions/native`
  (`taiki-e/install-action`, pinned by commit SHA as `scripts/check_ci_pins.py` requires, `tool:
  cargo-nextest@0.9.148`).
- Configuration in `.config/nextest.toml`. Profile `ci`: no fail-fast, failure output shown at once and again at the
  end, a slow-test report after 300 s (never a kill), JUnit at `target/nextest/ci/junit.xml`. The three tests whose
  assertion is a wall-time budget (`hosted_town`, `host_clock`, `hosted_punctuality`) run alone in the `timing` test
  group, because nextest runs tests of different binaries at the same time.
- `scripts/ci_shard.py` keeps the `ARC-110` partition (weighted, longest-processing-time first; nextest's own
  `--partition` is unweighted). Each shard's units become one `cargo nextest run --workspace --profile ci` with the
  same `--lib --bins --test NAME` target filters `cargo test` took, so the same tests run.
- **What stays on `cargo test`:**
  - doctests (`cargo test --doc`), which nextest does not run;
  - the three `harness = false` test targets (`launcher`, `arrival_resolvers_resume`, `kill_and_resume`). Their own
    `main` does not answer nextest's `--list` protocol. `ci_shard.py` names them in `CUSTOM_HARNESS`, and its
    self-test fails when a `harness = false` target exists that the set does not name;
  - the nightly `core-repeat` layer, whose flake classifier (`scripts/ci_repeat.py`) parses `cargo test`'s output.
- Every `core` job uploads its JUnit file as an artifact (`junit-<os>-<shard>`). `python3 scripts/ci_shard.py
  --weigh <junit.xml>...` turns them into a `WEIGHTS` table.

**Consequence for tests.** Nextest runs each test in its own process. A test may not depend on another test's
in-process state; the audit of 2026-10-27 found none (`git grep` for a `static` `Mutex`, `OnceLock`, `LazyLock` or
atomic shared between tests: only per-process counters for scratch names). Shared expensive work between tests must
go through files, as `pr-ci-test-economy.md` §1.4 specifies.

**Not done here.** Building one nextest archive per OS and running the shards from it (design §4 P1, about
115 runner-minutes per full run). It changes the jobs' shape (a build job feeding the shards) and is a follow-up
inside the same design.
