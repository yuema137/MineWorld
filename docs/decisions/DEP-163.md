## DEP-163 — cargo-nextest runs the `core` suite in CI

**Date** 2026-10-27 · **Status** accepted · **Approved by** operator ruling Q-3 of 2026-10-27 ("adopt cargo-nextest,
with a DEP record"), relayed by the primary session · **Relates to** `ARC-110` (the weighted shards), `ARC-154`
(milestone runs), `DEP-18` (the toolchain image) · **Design** `.structured-coding/plans/mvp0/pr-ci-test-economy.md`
§2.3, §5 P1

**Problem.** CI ran the `core` suite with `cargo test`. Three gaps followed from that runner. First, `cargo test`
writes no machine-readable per-test result, so the shard weights (`scripts/ci_shard.py` `WEIGHTS`) were
reconstructed by hand from log timestamps, and two heavy binaries were missing from the table. Second, a failing
test is found by scraping the log. Third, the per-PR `impact` job (Q-1) needs to select tests by an expression over
packages, binaries and test names, which `cargo test` cannot do in one command.

**Options compared.**

| Option | What it gives | Verdict |
| --- | --- | --- |
| **cargo-nextest** (Apache-2.0 OR MIT; Linux, macOS, Windows; maintained since 2022) | JUnit with each test's own time; filtersets (`package()`, `binary()`, `test()`, `rdeps()`); no fail-fast per profile; test groups for tests that must run alone; archives for build-once, run-many | **Adopt.** It runs our tests unchanged and stays a runner: world state, ownership and CI policy remain ours. |
| keep `cargo test`, parse its log | no new tool | Rejected: the weights stay hand-made, and selection by expression needs a second tool anyway. |
| `cargo test -- -Z unstable-options --format json` | per-test JSON | Rejected: needs a nightly compiler; the workspace pins stable 1.97.1. |

**Choice.**

- Version **0.9.148** (released 2026-10-08), pinned in the execution/provenance checker and two installers that must agree: the `Dockerfile` toolchain stage
  (`cargo install --locked cargo-nextest@0.9.148`, the `cargo-deny` pattern) and `.github/actions/native`
  (`taiki-e/install-action`, pinned by commit SHA as `scripts/check_ci_pins.py` requires, `tool:
  cargo-nextest@0.9.148`).
- Configuration in `.config/nextest.toml`. Profile `ci`: no fail-fast, failure output shown at once and again at the
  end, a slow-test report after 300 s (never a kill), JUnit at `target/nextest/ci/junit.xml`. The three tests whose
  assertion is a wall-time budget (`hosted_town`, `host_clock`, `hosted_punctuality`) run alone in the `timing` test
  group, because nextest runs tests of different binaries at the same time.
- `scripts/ci_shard.py` keeps the `ARC-110` partition (weighted, longest-processing-time first; nextest's own
  `--partition` is unweighted). Local builds retain Cargo target flags; archived shards translate the same
  units to nextest binary filtersets. Both paths select the same lib/bin/integration targets.
- **What stays on `cargo test`:**
  - doctests (`cargo test --doc`), which nextest does not run;
  - the three `harness = false` test targets (`launcher`, `arrival_resolvers_resume`, `kill_and_resume`). Their own
    `main` does not answer nextest's `--list` protocol. `ci_shard.py` names them in `CUSTOM_HARNESS`, and its
    self-test fails when a `harness = false` target exists that the set does not name;
  - the nightly `core-repeat` layer, whose flake classifier (`scripts/ci_repeat.py`) parses `cargo test`'s output.
- Every `core` job uploads its JUnit file as an artifact (`junit-<job>-<os>-<layer>-<shard>`). `python3 scripts/ci_shard.py
  --weigh <junit.xml>...` turns them into a `WEIGHTS` table.

**Consequence for tests.** Nextest runs each test in its own process. A test may not depend on another test's
in-process state; the audit of 2026-10-27 found none (`git grep` for a `static` `Mutex`, `OnceLock`, `LazyLock` or
atomic shared between tests: only per-process counters for scratch names). Shared expensive work between tests must
go through files, as `pr-ci-test-economy.md` §1.4 specifies.

**Archive completion (P1 recovery, 2026-11-22).** The preserved initial implementation deferred the
approved build-once requirement; that was incomplete, not a scope ruling. `core-archive` now builds one
nextest archive per OS on the same pinned runner/container as its consumers. Each weighted `core` shard
reads the artifact, verifies SHA-256, revision, absolute workspace, OS, architecture, Rust and nextest
identity, and selects its targets with filtersets; no regular test build runs in the consumer.

The artifact stays under `artifacts/core-archive`, outside the pruned Cargo cache. The workflow uploads
it only after a successful producer, with a required manifest and archive. Names are OS-specific within
one workflow run; producer reruns explicitly replace that artifact, while failed-shard reruns can reuse
the successful producer's artifact. Consumers never modify the uploaded archive. A missing artifact or
failed producer cannot make a green full-run gate: its required shards fail or skip, and the gate rejects
anything except success. All existing full/deferred triggers and gate names remain unchanged.

Tests embed absolute paths with `env!(CARGO_MANIFEST_DIR)` and `env!(CARGO_BIN_EXE_...)`. To preserve
assertions without modifying tests, the consumer requires the same absolute workspace path and extracts
to its original target directory (`--extract-to`, `--extract-overwrite`; nondefault target directories are refused), not nextest's default temporary
directory. Nextest archives the required non-test binaries. Arbitrary relocation is explicitly refused;
changing Rust tests for relocation is outside P1. The same checkout root on the same hosted runner label
is part of this CI deployment contract. The pinned tool's help and upstream
[archive documentation](https://nexte.st/docs/ci-features/archiving/) govern the flags.

Doctests and custom harnesses retain Cargo on their owning shard, including their necessary compilation;
nextest archives do not execute either protocol. Thus build-once applies to the regular nextest suite,
not the Cargo-only fallbacks. All units still occur exactly once. A new custom harness causes the producer
and fast self-test to refuse the stale audited set. Compile-time source paths, auxiliary executables,
weighted identity parity and failure continuation are covered by the dependency-free real fixture in
`scripts/test_ci_execution.py --integration`. `core-repeat` remains Cargo-based; its Python wrapper is
recognized as a test run so later commands continue after failure, preserving P0.

Nextest's JUnit is parsed for diagnostic failure identities, including error/timeout records. Missing or
malformed results cannot make a successful nextest command green. Process exit status remains authoritative;
a parsed report never clears a failed status. Aggregation refuses duplicate identities, absent/malformed
records, negative/nonfinite durations and failed/incomplete timings rather than producing misleading weights.
Cargo-only timings are not in JUnit and their existing weights must be retained during table updates.
The version in `ci_archive.py`, Dockerfile and native action is mechanically checked for agreement.

Local validation is recorded separately from the final full milestone CI obligation in the P1 ledger.
No cross-OS/full-suite PASS is implied by local macOS fixture evidence.
