# Startup presentation

The optional loading layer in `loading/loading.gd` is Godot presentation only. The neutral bundled runtime and the source 3D scene adopt it at `res://mineworld_loading/` via symlinks. It owns no world, settings, network or save state and loads no imported assets. A single root-owned CanvasLayer survives the runtime's scene replacement; adding it is deferred and its ready signal is awaited before use because an entry scene's ready runs while the root is adding children.

The bundled runtime renders the screen before mounting its selected pack, applies the existing settings table unchanged, then uses Godot's threaded resource loader. Its bar reports only the engine's scene-resource fraction, never overall launch progress. Only a LOADED status permits retrieval. Request/status/scene errors retain runtime exit 2 after a rendered named error. The 2D completion is connected directly to the layer from SceneTree.scene_changed, since the boot node is freed by that transition. It means the client scene has been rendered, not that a server accepted a player.

The 3D entry scene reuses that layer, or creates it when run from source. It preserves setup order and yields a completed render between settings/layout/world/people/light/player/join stages. Until setup is complete, its frame/input handlers do not read unfinished objects. Input remains held and the mouse visible through SliceLink.has_first_view and the final rendered frame, then previous capture is restored. Link status is worded through existing catalogs and displayed while joining; existing reconnect/refusal policies are unchanged. Offline starts need no network observation. Refusals keep their original displayed messages and scripted exit codes.

`drawn` waits on process_frame then RenderingServer.frame_post_draw; headless execution waits only process_frame. The draw wait is bounded in process frames, not time: Godot draws nothing while no window can draw (on macOS a window wholly covered or minimised), so frame_post_draw never fires, and an unbounded wait paused startup for as long as the window stayed covered (measured 5-227 s, 2026-11-27). After `UNDRAWN_FRAMES` (3) process frames without a draw, `drawn` returns false, logs `window not drawing (covered or minimised); loading continues` once, and loading proceeds; a draw that is merely slow (a cold pipeline compile) delays the following process frame as well and is still waited for in full. That holds only while drawing runs on the main thread (the default `rendering/driver/threads/thread_model`, which no MineWorld project overrides); if rendering moves to a separate thread, `UNDRAWN_FRAMES` must be revisited. Undrawn, the 3D finish logs `client scene ready (window not drawing)` instead of `client scene visible`, and a runtime error still exits 2 with its named line logged, though no frame showed it. The next frame the window draws shows the current stage. Startup logs use engine monotonic ticks. A headless 'loading UI drawn' marker is a scheduling marker, not visual proof. `client scene visible` in 3D follows a real first view when connected; in 2D it follows scene creation. Elapsed time is measured time, never an estimate. Pack mount, runtime glTF world construction and GI baking remain synchronous; the current stage can be stationary and input cannot run inside those indivisible engine calls. No quality reduction or overall time improvement is promised.

Authoritative API references: Godot's Background loading tutorial and RenderingServer frame_post_draw documentation. The loader polls status before get to avoid reintroducing a blocking scene read; main-thread tree mutation and GPU preparation are not claimed to become background work.

**First camera frame (2026-11-27, perf lane evidence `perf-startup/target/perf-evidence/`).** The first frame drawn through the player's camera compiles the render pipelines. On a cold macOS Metal shader cache, Godot 4.7.2 spends about 117 s in that single frame. Nothing is redrawn meanwhile: the stage text and the elapsed timer stay as last drawn. The 3D entry therefore draws one frame with 3D disabled right after creating the player. That frame shows `loading.graphics` ("Preparing graphics... (the first launch can take a few minutes)"), so this is the text on screen during the wait. 3D is then restored, unchanged. The stage shows no percentage and makes no estimate. A warm cache makes the stage brief.
